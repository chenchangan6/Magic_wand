# Magic Wand 局域网配置页 - 交接文档

> 写给下一个接手的模型。  
> 这份文档不是简述，而是当前项目的真实状态、目标、边界、数据结构、页面职责、业务流程和后续实施顺序。  
> 目标只有一个：**让至少一局游戏从创建到结束真正跑通**，并且保住已经打通的控制端链路。

---

## 1. 项目最终目标

这个项目不是只做一个漂亮的网页，而是做一个完整的“魔杖游戏配置与运行系统”。

最终目标是让使用者能够在电脑端完成下面这条真实流程：

`创建房间 -> 选择模板 -> 配设备组 -> 配分组规则 -> 配灯效与感应方式 -> 保存草稿 -> 开始游戏 -> 结束并留记录`

首个必须跑通的示例玩法是：

**多人寻宝混战**

只要这一条链路能完整跑通，就说明系统不是纯展示页，而是真正能开局的系统。

---

## 2. 当前项目的原则边界

以下原则是硬约束，不应轻易打破：

1. **不要破坏已经打通的控制端链路**
   - 读取控制端
   - 扫描设备
   - 点名
   - 一键发布
   - 控制端配置导入协议

2. **前端优先**
   - 先解决 UI 结构、状态流转、房间模型、模板/功能分层。
   - 非必要不要改后端。

3. **只使用官方 Tailwind utility class**
   - 不要再发明自己的 CSS 框架。
   - 不要把页面重新做成自定义 class 系统。
   - 不要依赖网络 CDN。
   - 图标优先使用本地内联 SVG / Heroicons 风格。

4. **不能再用“看起来像按钮”的东西糊弄业务**
   - 如果是按钮，就必须接真实逻辑。
   - 如果暂时没有逻辑，就把它明确做成展示态。

5. **黄金路径优先**
   - 先让一局游戏真正能跑通。
   - 再去做更细的配置优化。

## 5. 现在真正需要修正的业务模型

这是整个项目的关键。  
现在不是“按钮没接上”，而是**游戏对象模型**没有完全对齐。

### 5.1 房间模型必须变成多房间并存

以前的思路过于单房间化。  
现在必须明确：

- `rooms[]` 才是主对象
- `active_room_id` 只是当前 UI 选中的房间
- `current_room` 只是兼容字段，不应再是唯一中心

每个房间都是独立实例，可并存：

- 同一个模板可以开多个房间
- 不同房间可以绑定不同设备组
- 不同房间可以同时处于草稿、进行中、已结束状态

### 5.2 房间状态必须清晰

房间至少要有：

- `draft`：草稿
- `running`：进行中
- `ended`：已结束

房间流转应当是：

1. 创建草稿
2. 配置源组 / 目标组 / 模板
3. 保存草稿
4. 开始后切为 running
5. 结束后切为 ended
6. 记录写入本地历史

### 5.3 游戏三层分离

项目的核心概念必须拆开，不能再混：

#### 游戏功能
能力积木，不是房间，不是模板。

应包含：

- 感应方式
- RSSI 映射
- 保持时间
- 计分灯
- 默认空闲灯效
- 触发灯效

#### 游戏模板
完整玩法包，适合复用。

应包含：

- 模板名
- 模板说明
- 适用场景
- 默认源组建议
- 默认目标组建议
- 默认感应规则
- 默认灯效组合
- 默认计分方式

#### 游戏房间
一次实际开局的实例。

应包含：

- 房间名
- 选择的模板
- 源组
- 目标组
- 房间备注
- 状态
- 开始/结束时间
- 本局结果
- 本地历史

## 6. 目标玩法：多人寻宝混战

下一个模型必须把“多人寻宝混战”作为第一条黄金路径，而不是只做概念。

### 6.1 玩法说明

这是一种典型的寻宝玩法：

- 一组魔杖作为源组
- 一组宝箱作为目标组
- 魔杖靠近宝箱后触发感应
- 满足条件后点亮、计分、记录找到结果
- 一局结束后可统计成绩

### 6.2 典型使用方式

假设现场有 4 个孩子：

- 开 1 个“多人寻宝混战”房间
- 绑定一套魔杖组和宝箱组
- 使用对应灯效和感应规则
- 开局后每个孩子可拿到自己的设备

再来 8 个孩子时：

- 可以再开另一个同模板房间
- 但绑定另一套设备组
- 两局并行互不干扰

### 6.3 这个模板要包含什么

“多人寻宝混战”作为模板，至少要有：

- 房间说明
- 源组建议
- 目标组建议
- 感应方式建议
- 触发灯效
- 默认空闲灯效
- 计分灯
- 结束后的记录说明

### 6.4 这个模板的验收标准

必须能够：

1. 从向导创建该房间
2. 选模板
3. 选源组 / 目标组
4. 选感应方式和灯效
5. 保存草稿
6. 开始游戏
7. 结束游戏
8. 在本地生成历史记录

## 7. 向导的正确职责

向导不是“把所有功能再做一遍”，而是把一局游戏串起来。

### 7.1 向导固定 4 步

1. 输入房间名称
2. 选择游戏模板
3. 选择源组 / 目标组
4. 检查摘要并开始

### 7.2 向导要解决的问题

向导存在的意义是让第一次使用的人也能完成开局。

因此向导必须：

- 不依赖用户理解所有底层概念
- 允许保存草稿
- 允许返回上一步
- 不完整时拦截开始
- 只服务开局流程

### 7.3 向导不应该做的事

不要在向导里再堆一堆复杂编辑器：

- 不要把游戏功能全搬进去
- 不要把模板编辑器塞进去
- 不要把房间历史塞进去
- 不要把分组管理完全重做一遍

它只负责把已有能力拼成一局。

## 8. 页面职责边界

### 8.1 首页 / 总览

首页只保留高频操作和总览：

- 读取控制端
- 一键发布
- 扫描设备
- 点名
- 本地草稿
- 模板入口
- 房间入口
- 总览统计
- 调试日志（可折叠）

首页不要再塞大长条的编辑区。

### 8.2 设备页

设备页负责：

- 设备名编辑
- 分组分配
- 按分组筛选
- RSSI 排序
- 离线设备展示

要求：

- 离线设备不要显示 RSSI
- 离线设备不要显示点名
- 离线设备不要显示保存设备
- 设备名称可编辑，保存/取消逻辑清楚

### 8.3 分组页

分组页负责：

- 真实分组列表
- 新建分组
- 编辑分组
- 保存分组
- 删除分组
- 绑定设备
- 设目标关系

分组不能只是“看起来能点”的卡片。

### 8.4 游戏功能页

游戏功能页只负责能力积木，不负责房间开局。

应包含：

- 感应方式
- RSSI 阈值
- 保持时间
- 计分规则
- 灯效绑定

### 8.5 灯效库页

灯效库页是独立模板库，不是房间配置页。

应支持：

- 新建灯效
- 复制灯效
- 删除灯效
- 预览灯效

### 8.6 预览台

预览台负责展示效果，不承担业务逻辑。

### 8.7 游戏模板页

模板页负责管理完整玩法包。

应支持：

- 新建模板
- 复制模板
- 保存当前配置为模板
- 删除模板
- 选择模板作为房间默认值

### 8.8 游戏房间页

房间页负责一次实际开局的实例管理。

应支持：

- 新建房间
- 选中当前房间
- 继续编辑草稿
- 开始游戏
- 结束游戏
- 删除房间
- 查看房间历史

### 8.9 调试页

调试页只负责：

- 读取原始日志
- 查看错误
- 排查发布
- 排查代理

## 9. 记录与持久化要求

### 9.1 本地草稿

记录建议包含：

- 房间名
- 模板名
- 开始时间
- 结束时间
- 时长
- 源组
- 目标组
- 房间状态
- 备注
- 房间摘要

### 9.3 历史保存位置

历史记录只保存在电脑本地，不进入控制端导入包。

建议：

- 追加式 JSONL
- 后续方便统计和回放

## 11. 已经不能再继续“假装可用”的地方

以下问题不能再只做视觉修补：

1. 房间只能有一个时，房间概念就错了。
2. 模板只是说明文字时，模板概念也错了。
3. 游戏功能和向导混在一起时，流程就会越来越乱。
4. 只改按钮不改状态，会制造更多假可用控件。
5. 只修界面不修模型，最终还是无法完成开局闭环。

所以剩余工作必须优先修模型和状态，而不是继续只抠按钮外观。

### 15.1 CSS 和样式

1. **MUST：离线使用官方 Tailwind**
   - 只能使用项目本地已经安装好的 Tailwind 工具链。
   - NEVER 使用 CDN。
   - NEVER 自己重写一套 CSS 框架。
   - NEVER 再造一套自定义 class 体系来替代 Tailwind。

2. **MUST：样式优先只改前端**
   - 页面布局、按钮密度、字体、间距、颜色、图标等，优先在本地端前端解决。
   - NEVER 因为“想更好看”就碰后端。
   - 只有在功能冲突或数据模型冲突时，才允许讨论后端改动。

3. **MUST：不要反复在旧 CSS 上打补丁**
   - 如果旧的自定义样式已经导致结构混乱，立即停止在旧规则上继续加补丁。
   - 优先用 Tailwind utility class 重新组织界面。
   - 如果要改布局，必须在结构层调整，而不是继续往旧规则里追加新规则。

### 15.2 后端和已打通逻辑

1. **MUST NOT：轻易篡改已经打通的后端代码**
   - 已经工作的控制端读取、扫描、点名、一键发布、配置导入，必须默认保持原样。
   - 只有在明确存在功能冲突、数据格式冲突或协议冲突时，才允许改后端或控制端协议。
   - NEVER 为了修 UI 顺手重构后端。

2. **MUST：先确认问题是不是前端层**
   - 如果是按钮样式、布局、可见性、选中态、折叠态、输入提示，这些先在前端解决。
   - 只有当业务对象模型确实不够用，才考虑改状态结构。
   - 只有当状态结构不足以表达业务时，才考虑后端协同改动。

### 15.3 乱码和编码问题

这是非常重要的一条经验，因为之前这个项目里已经多次出现过中文乱码。

1. **MUST：所有新文件统一 UTF-8**
   - 新建或重写 `.js`、`.html`、`.md`、`.json` 时，一律使用 UTF-8。
   - NEVER 用系统默认编码去写中文内容。
   - NEVER 让 PowerShell 或编辑器用错误代码页把中文写坏。

2. **MUST：检查中文字符串是否真的正常显示**
   - 如果发现类似“绯庡”“鍒濆”“灞傘€”之类的字符，必须优先判断为编码问题。
   - 先检查源文件编码，再检查浏览器显示，再检查生成文件。
   - 如果 JS 里有中文常量、模板名、设备名示例、按钮标签，必须肉眼确认它们在页面里正常显示。

3. **MUST：读文件时注意编码**
   - 在 PowerShell 里查看源文件时，必须使用明确编码，例如 UTF-8。
   - NEVER 用默认编码去判断文件内容是否正常。
   - 如果需要批量生成或修改文本，先确认生成工具的编码行为。

4. **MUST：生成后的页面要做一次真实浏览器检查**
   - NEVER 只看文件内容。
   - 必须打开本地页面，确认中文、图标、按钮、标签页、摘要文本是否都正常。
   - 如果有任何乱码，必须先从编码链路排查。

### 15.4 交付习惯

1. **MUST：先让逻辑对齐，再让视觉变好**
   - 这个项目不是单纯的 UI 项目。
   - 视觉可以后调，但逻辑模型必须先对。

2. **MUST：任何新页面都要和旧流程兼容**
   - 如果新增向导、模板、房间页，必须确认它们不破坏旧入口。
   - 如果旧按钮还存在，就不能让它变成假入口。

3. **MUST：如果暂时没法做真功能，就明确标成展示态**
   - NEVER 让用户点了没反应，还以为系统坏了。
   - 比起假可用，明确不可用更诚实，也更不容易误导后续调试。

### 15.5 执行前自检清单

下一个模型在开始任何修改前，必须先自检以下问题：

- 这次改动是否会影响 `/api/controller/*` 现有链路？
- 这次改动是否只是 UI，却意外碰到了后端？
- 这次改动是否会把 `rooms[]`、`active_room_id`、`templates[]` 的关系弄乱？
- 这次改动是否新增了乱码风险？
- 这次改动是否会让一个“看起来能点”的控件变成假入口？

如果任意一个答案不清楚，先停下来查代码，不要直接改。
